\chapter{Introduction}

This book is an introduction to chip design using open-source tools. It covers the steps needed to produce a chip for a design described in a hardware description language (HDL), down to the files that are sent to the fab. Those steps are often called the backend design.

\section{Tool Installation}

The magic of open-source tools is that we can install them on a personal computer without any concerns of licensing and license servers. The downside of open-source tools is the variety of installation options. There is no single best way for the installation. Furthermore, open-source tools are best supported on a Unix operating system, and preferably Linux. Support under macOS comes second. MS Windows is best served by using the Windows Subsystem for Linux.


\subsection{Nix Based}

From OpenLane2 (now LibreLane) on, the preferred installation is \myref{https://en.wikipedia.org/wiki/Nix_(package_manager)}{Nix}-based. Nix is a cross-platform package manager that also provides native binaries for x86 and ARM-based systems (e.g., Mac laptops). The LibreLane 
\myref{https://librelane.readthedocs.io/en/latest/installation/index.html}{installation} documentation explains how to install Nix, and also how to set up the Nix cache for the LibreLane tools.

Another option to install Nix is via \myref{https://docs.determinate.systems/}{Determinate}. Note that you need to install the LibreLane cache to avoid building all the tools yourself.

\subsection{Docker Images}

Another option is to use Docker containers with ready-installed tools.
Harald Prettl, from the Johannes Kepler University of Linz, provides 
\myref{https://github.com/iic-jku/IIC-OSIC-TOOLS}{IIC-OSIC-TOOLS} (Integrated Infrastructure for Collaborative Open Source IC Tools), a Docker container based on Ubuntu 24.04 LTS for the following
CPU architectures: x86\_64/amd64 and aarch64/arm64.

The folder \code{/foss/designs} is the place to access user data on your local machine. It points to the directory pointed by the environment variable \code{DESIGNS}, the default is \code{$HOME/eda/designs}. To change this to start with your home folder, invoke the Docker image with:

\begin{verbatim}
DESIGNS=$HOME ./start_x.sh
\end{verbatim}

Note that, as of the time of writing, the default PDK is the IHP PDK, which is not yet supported in the LibreLane flow from within the container.\footnote{See: \url{https://github.com/iic-jku/IIC-OSIC-TOOLS/issues/147}} Switch to the Sky130 PDK with the following command:

\begin{verbatim}
sak-pdk sky130A
\end{verbatim}


\subsection{Compiling from Source}

As the tools are open-source, it is always a (theoretical) option to compile them from source. However, often there are library dependencies that are not easy to resolve. Therefore, we recommend installing the tools with some packaging software that ensures compatibility between the various tools.


\subsection{Installing LibreLane}

When you use the \code{nix}-based setup, you need to install \myref{https://github.com/librelane/librelane}{LibreLane}. Install LibreLane by cloning it:

\begin{verbatim}
git clone git@github.com:librelane/librelane.git
\end{verbatim}

\noindent You set up your environment by entering \code{nix} as follows:

\begin{verbatim}
cd librelane
nix-shell
\end{verbatim}

\noindent The frontend command is \code{librelane}. Check the version you have installed with:

\begin{verbatim}
librelane --version
\end{verbatim}

LibreLane also installs the Sky130 PDK using the \code{ciel} tool. The PDKs are stored under \code{$HOME:/.ciel}.

\subsection{Further Packages}

There are several other distributions of the open-source chip design tools available:

\begin{description}
\item[\myref{https://github.com/YosysHQ/oss-cad-suite-build}{OSS CAD Suite}] is a collection of tools with a focus on open-source design flow for \myref{https://en.wikipedia.org/wiki/Field-programmable_gate_array}{FPGA}s.
\item[\myref{https://yowasp.org/}{YoWASP}] (Yosys WebAssembly Synthesis \& PnR) is a collection of tools targeting FPGA design flow compiled to WebAssembly. Therefore, they can be easily run on different platforms, even as a Visual Studio Code plugin. 
\end{description}

\subsection{Exploring the Design}

A first step to explore the design is to view the GDS in KLayout with:

\begin{verbatim}
librelane --last-run --flow openinklayout adder.yaml
\end{verbatim}

In Klayout, you can explore the design. Use the rulers to measure your design. How large is it?
Would it fit into a Tiny Tapeout Tile? How large is a Tiny Tapeout tile?
When you expand the adder in Cells, you can see which cells have been used.
By double-clicking on a cell type, it is removed from the display. This is an indirect way to show the cells in the GDS. The flip-flop standard cells in Sky130 have names that include ``dfxtp'' in their name. Double-click that cell to see how many flip-flops are used. How many should there be?

Another option is to open the design with the OpenROAD viewer:
\begin{verbatim}
librelane --last-run --flow openinopenroad adder.yaml
\end{verbatim}

Matt Venn has a good selection of layers and color assignments at \myref{https://github.com/mattvenn/librelane_summary/blob/librelane/klayout_gds.xml}{klayout\_gds.xml}. You can use it with klayout as follows:
\begin{verbatim}
klayout -l klayout_gds
\end{verbatim}

That configuration file is part of the \myref{https://github.com/mattvenn/librelane_summary}{summary tools}, which can be used for a quick exploration of the design. Clone the repository, add it to your path, and set the \code{PDK_ROOT} variable (easiest into a file that you source, or add those lines to your \code{$HOME/.bashrc}):

\begin{verbatim}
export PATH=$PATH:$HOME/path/to/librelane_summary
export PDK_ROOT=$HOME/.ciel
\end{verbatim}

Explore the tool with:

\begin{verbatim}
summary.py --help
\end{verbatim}

When in a folder that contains the LibreLane runs, explore the GDS of the latest run with:
\begin{verbatim}
summary.py --gds
\end{verbatim}

\chapter{Open-Source Production Frameworks}

Chip design consists of several steps from synthesis down to GDSII files. Scripts usually orchestrate those steps. In the following, we describe different frameworks that contain the needed open-source tool, but also the scripts to run the flow.

\section{OpenROAD}

\myref{https://github.com/The-OpenROAD-Project}{OpenROAD}~\cite{OpenROAD} started as a DARPA-sponsored project to enable an end-to-end design flow of chips from RTL to the final chips without human intervention, within a maximum of 24 hours. The documentation is published on \myref{https://openroad.readthedocs.io/en/latest/}{Read the Docs}.
OpenROAD includes the following open-source \myref{https://openlane.readthedocs.io/en/latest/flow_overview.html}{tools}:

\begin{itemize}
\item \myref{https://github.com/the-openroad-project/openroad/tree/master/src/ifp}{ifp} defines the core area, the rows, and the tracks.
\item \myref{https://github.com/the-openroad-project/openroad/tree/master/src/pdn}{pdn} is a power distribution network (PDN) generator.
\item \myref{https://github.com/the-openroad-project/openroad/tree/master/src/tap}{Tapcell} inserts tapcells or endcaps.
\item \myref{https://github.com/the-openroad-project/openroad/tree/master/src/gpl}{gpl} performs global placement. The tool is an extension of the \myref{https://github.com/The-OpenROAD-Project/RePlAce}{RePlAce} tool.
\item \myref{https://github.com/the-openroad-project/openroad/tree/master/src/rsz}{Gate Resizer} to optimize the design until the maximum utilization is reached.
\item \myref{https://github.com/the-openroad-project/openroad/tree/master/src/dpl}{OpenDP} performs detailed placements.
\item \myref{https://github.com/the-openroad-project/openroad/tree/master/src/cts}{TritonCTS 2.0} is performs clock tree synthesis.
\item \myref{https://github.com/the-openroad-project/openroad/tree/master/src/grt}{FastRoute} performs global routing.
\item \myref{https://github.com/the-openroad-project/openroad/tree/master/src/drt}{TritonRoute} performs detailed routing.
\item \myref{https://github.com/the-openroad-project/openroad/tree/master/src/rcx}{OpenRCX} performs parasitics extraction.
\item And some more.
\end{itemize}

Use the links for documentation of the individual tools.

\section{Caravel}

\myref{https://caravel-harness.readthedocs.io/}{Caravel} is a SoC framework developed by Efabless for the Google/Skywater 130nm Open PDK. It is the basis for the \myref{https://chipfoundry.io/chipignite}{chipIgnite} MPW shuttles.
It contains a padframe, a houskeeping block, a management area including a RISC-V core, and a user project wrapper.
The user area is 3000\;{\textmu}m x 3600\;{\textmu}m (10 mm$^2$). To put this into perspective, a simple 3-stage RISC-V pipeline, such as Wildcat~\cite{wildcat:arcs2025}, fits into a 0.2 mm$^2$ area. A 4~KiB memory from eFabless has a 0.18 mm$^2$ area.

ChipFoundry now maintains Caravel. Note that the transition to ChipFoundry is still in progress; therefore, some documentation still contains the eFabless name. Additionally, some datasheets are outdated (e.g., referring to the PicoRV as the management processor, which is now the \myref{https://github.com/SpinalHDL/VexRiscv}{VexRiscv}).

\begin{figure}
  \centering
  \includegraphics[width=\textwidth]{figures/layout}
  \caption{The combination of the Caravel harness with the user project results in the final Caravel tile for the MPW run. Copyright 2020-2022 Efabless Corporation and contributors, License: Apache 2.0.}
  \label{fig:layout}
\end{figure}

Caravel is, in fact, two artifacts that are combined during the MPW chip production. The Caravel harness, which combines the RISC-V CPU and IO management with the user project, is used to build the final Caravel tile.
Figure~\ref{fig:layout} shows this combination of the two components to the final Caravel. The so-called \code{user_project_wrapper} is the design that is submitted to ChipFoundry. As users, we do not need to directly deal with the Caravel harness.


\subsection{Caravel Harness}

\begin{figure}
  \centering
  \includegraphics[width=\textwidth]{figures/caravel}
  \caption{The Caravel Harness}
  \label{fig:caravel}
\end{figure}

Figure~\ref{fig:caravel} shows a simplified block diagram of the Caravel harness.
The Caravel harness contains the \myref{https://github.com/chipfoundry/caravel_mgmt_soc_litex}{management core}, the user project, the padframe, and GPIOs configured by an SPI controller.

The management core contains a \myref{https://github.com/SpinalHDL/VexRiscv}{VexRiscv} RISC-V core, 
256-word memory (latch-based), shared for instruction and data, and peripherals, connected via a Wishbone bus. The peripherals include a flash controller, a UART, an SPI master, and a logic analyzer. The Wishbone bus and the logic analyzer are connected to the user area.
The management core is built with the \myref{https://github.com/enjoy-digital/litex}{LiteX} framework, which itself uses \myref{https://github.com/m-labs/migen}{Migen}, a Python project to build digital hardware.

The RISC-V core in the management runs firmware out of the Flash to configure the user project GPIOs, interact with the user area via the Wishbone bus, and interact with the logic analyzer.

The user project is connected to the GPIO pins, the Wishbone bus of the RISC-V CPU, the logic analyzer, and interrupt pins to the RISC-V CPU. The example components are split into a wrapper and the \emph{real} component. For example, the user project is split into a \code{user_project_wrapper} and a \code{user_proj_example}.

The chipIgnite project includes a \myref{https://github.com/fossi-foundation/caravel_board}{board} containing the Caravel chip, a power supply, a serial Flash for the firmware, and an FTDI FT232 for communication between a PC via USB. 


\subsection{Caravel User Project}

The Caravel framework itself is split into two repositories: the \myref{https://github.com/chipfoundry/caravel_user_project}{user project} (often called \code{user_project_wrapper}, as this is the top-level of the user project) and \myref{https://github.com/chipfoundry/caravel}{Caravel} itself. The example user project contains a tiny example (a counter) to get started. Within that project, all the needed tools are installed, including a lite version of Caravel, the management core for simulation, LibreLane, and the Sky130 PDK.

The starting point is the user project. The flow is run within Docker. Follow the instructions in the \myref{https://github.com/chipfoundry/caravel_user_project/blob/main/docs/source/index.md}{Caravel User Project}. The dependencies on Docker and Python are listed there. Missing is the dependency on two Python libraries: \code{python-tk} and \code{Click}.

There are two ways to integrate your design into Caravel: (1) Harden your user project first and then instantiate it in the wrapper as a hard macro, and then run the hardening of the wrapper; (2) Harden the whole project at once (include your user project as Verilog files in the wrapper configuration). The example project performs the individual hardening.

Following \myref{https://www.youtube.com/watch?v=YWj4HhRU36U&t=302s}{video} from ChipFoundry gives an overview of the flow of the example project. Then follow the instructions in the \myref{https://github.com/chipfoundry/caravel_user_project/blob/main/docs/source/index.md}{Caravel User Project}.

\subsection{Setup}

Start by cloning the \myref{https://github.com/chipfoundry/caravel_user_project}{user project} by selecting \emph{Use this template}. Install the prerequisites and clone your repository. Note that the project requires several GB of space on your hard disc. The initial clone is 1/4 GB. The needed tools are installed with:

\begin{verbatim}
make setup
\end{verbatim}

\subsection{Hardening the User Project}


The example project consists of a simple 16-bit counter that is connected to the \myref{https://en.wikipedia.org/wiki/Wishbone_(computer_bus)}{Wishbone} bus, the logic analyzer, and 16 output pins.
With the Wishbone connection, the counter can be controlled (i.e., started and stopped) from the management core.
The source can be found in \code{verilog/rtl/user_proj_example.v}.

To get started, we recommend hardening and testing the user project as it is.  After you have successfully hardened and tested the example, add your modules to the project. The default configuration is set up to harden the user project first and include the GDS as a hard macro in the wrapper project.

The \myref{https://github.com/chipfoundry/caravel_user_project}{user project} contains two projects in folder \code{openlane}:
\begin{enumerate}
\item \code{user\_proj\_example} and
\item  \code{user\_project\_wrapper}
\end{enumerate}

To simplify the hardening, it is recommended to keep those names.\footnote{Although a name that includes a word such as \emph{example} sounds a bit silly, most projects keep the names.} Both folders contain a \code{config.json} for the LibreLane run. Explore the two configuration files. You will see that the die area for the user project is set to 2800\;{\textmu}m x 1760\;{\textmu}m, which is smaller than the available 10 mm2 on the Caravel project. Change this setting later to fit your design. In the configuration file of the wrapper, we can see that the user project is instantiated as a hard macro at position \code{[60, 15]}.

The user project is hardened with:
\begin{verbatim}
make user_proj_example
\end{verbatim}

That command starts the hardening of the user project with LibreLane, generating the GDS file and a gate-level netlist with instances of the Sky130 standard cells for gate-level simulation. That GDS can be found in folder \code{gds}. Use e.g., KLayout to explore that hard macro. The gate-level netlist in folder \code{verilog/gl}. The LibreLane reports and generated files can be found in the folder \code{openlane/user_proj_example/runs}.

The project now needs 10 GB of disk space. Note that many of the generated files have already been committed to the original git repository, which creates annoying false source changes. Avoid committing those changes after every run.

The default configuration uses Docker to run the LibreLane tools. Depending on your setup (processor and operating system), running with Docker can be significantly slower than running the tools natively. For example, the user project required 2 hours to harden on my Mac with an M1. Most of the time was spent on magic spice extraction (1h30). When running it natively using Nix, the whole run executes in 15'. You can select Nix with:

\begin{verbatim}
make user_proj_example LIBRELANE_USE_NIX=1
\end{verbatim}

The next step is to harden the project wrapper with:
\begin{verbatim}
make user_project_wrapper
\end{verbatim}

This wrapper includes the user project as a hard macro. Similar to the user project, the run generates the GDS file and the Verilog file for gate-level simulation. The GDS file is the one that is submitted to the fab for production. The project has expanded to 11\;GB.

Caravel uses the \myref{https://en.wikipedia.org/wiki/Wishbone_(computer_bus)}{Wishbone}~\cite{soc:wishbone} bus to interface the processor core with the user design.
Wishbone is an open-source bus definition intended to be used on-chip.
The Wishbone specification defines a point-to-point communication.
Wishbone is a public domain standard used by several open-source IP cores.

\subsubsection{The Wishbone Bus}

Figure~\ref{fig:wishbone} shows the connection between a Wishbone master and a Wishbone servant.
Wishbone is a simple request/acknowledgment interface. The master signals a request by asserting \code{SEL_O} and \code{STB_O}.
An asynchronous slave can, in the same cycle, reply with \code{ACK_O}.
A synchronous slave can delay the acknowledgment.
The master needs to hold the address, data, and control signals valid through the whole read or write cycle.

Although the bus specification is relatively simple, the Wishbone documentation is a bit lengthy, with 128 pages.
However, we can follow RULE 3.40 and PERMISSION 3.10 from the specification to build simple Wishbone devices.

\medskip

Rule 3.40:
\begin{quotation}
As a minimum, the master interface must include the following signals: \code{ACK\_I}, \code{CLK\_I}, \code{CYC\_O}, \code{RST\_I}, and \code{STB\_O}. As a minimum, the slave interface must include the following signals: \code{ACK\_O}, \code{CLK\_I}, \code{CYC\_I}, \code{STB\_I}, and \code{RST\_I}. All other signals are optional.
\end{quotation}

Permission 3.10:
\begin{quotation}
If in standard mode, the slave guarantees it can keep pace with all master interfaces, and if the \code{ERR\_I} and \code{RTY\_I} signals are not used, then the slave's \code{ACK\_O} signal may be tied to the logical AND of the slave's \code{STB\_I} and \code{CYC\_I} inputs. The interface will function normally under these circumstances.
\end{quotation}

Of course, to build a useful peripheral device, we also need to include the address, data in and out, and write enable signals.

Having this combinational loop from the master to the device and back to the master can lead to large combinational circuits when several devices are connected to the Wishbone bus. To break this loop, the \code{ACK} signal can be registered, leading to a two-clock-cycle-long transaction. This configuration is called a synchronous slave in the Wishbone specification. Figure~\ref{fig:sync:timing} shows the timing diagram for a read and write on a synchronous device.


The latest Wishbone specification (B4) adds a pipelined definition.
Note that the specification now includes two different, not necessarily compatible, specifications.
The non-pipelined access is then called Wishbone \emph{classic}.
The pipelined mode has the following Issue: the slave does not know if the master will issue a pipelined request. It would need to observe changing addresses, which is not practical. To be on the safe side, a synchronous slave would need to assert \code{STALL\_O}. However, as the Wishbone interface of the Caravel user project does not include a \code{STALL\_I} input, we assume that there will be no pipelined Wishbone transaction.

\section{Tiny Tapeout}

\myref{https://tinytapeout.com/}{Tiny Tapeout} is a project that takes the idea of a multi-project wafer to the next level. Tiny Tapeout uses one tile of an MPW shuttle on Skywater130 or IHP and divides that tile into 512 smaller tiles. We can now harden the design by running:

\begin{verbatim}

\end{verbatim}

\chapter{Memories}

When describing memories in an HDL, the synthesis tool will not generate on-chip memories, as we are used to in an FPGA. It will use generated storage out of DFF and multiplexers, which is very expensive. As an example, a 1024-bit memory is needed to implement the register file for an RISC-V processor. Implementing an RV-32I version in a 3-stage pipeline, the register file needs 320\;{\textmu}m x 320\;{\textmu}m or about 55\% of the processor area~\cite{wildcat:2024}.

An efficient memory cell is built out of six-transistor (6T) SRAM cells, as shown in Figure~\ref{fig:sram:cell}. The middle four transistors implement two cross-coupled inverters. The other two transistors are used for reading and writing the bit.
